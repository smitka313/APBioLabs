# Instructions for AI agents working on this repository

You maintain **AP Bio Digital Lab Bench** ([biologylabbench.com](https://biologylabbench.com); repo `smitka313/APBioLabs`), a free, no-login set of 13 interactive AP Biology labs plus "Biology Companion Activities" for OpenSciEd units. The owner, Robert Smitka, is a high-school biology teacher. Students and teachers rely on it in class, so correctness and reliability come before new features, and everything a student sees should look and behave like a polished, professional science tool.

## How the site is built

- Static HTML/CSS/JS, no framework or build step. Hosted on Cloudflare Pages at the site root; the old `smitka313.github.io/APBioLabs/` address redirects there (`domain-redirect.js`, `404.html`).
- Shared code:
  - `lab.js`: the global `Lab` toolkit (identity and Dataset IDs, seeded randomness, saving, reports, `Lab.chart`, `Lab.table`, timelapse/GIF).
  - `style.css`: design tokens, light/dark.
  - `scope.js`: the microscope.
- Each lab is `labNN.html`. The OpenSciEd companion is `openscied-b3-cell-cycle.*` plus `cell-cycle-scene.js` and `growth-model-scene.js`.
- Reuse the shared toolkit and the existing visual vocabulary before writing anything new. Read `KIT.md` and two or three existing labs first so new work matches them.
- Student work lives only in the browser (localStorage keys `aplab:*`). Never break saved keys, Dataset IDs or old saves; add migrations instead.
- Head/SEO blocks between `seo` markers are generated by `tools/build-seo.py`. Edit `tools/seo-content.json` or the script, never the generated block by hand. Check with `python3 tools/build-seo.py --check`.
- Teacher notes are AES-GCM-encrypted pages built with `tools/encrypt-notes.js` from plaintext sources that are **not** in the repo. Never commit plaintext notes or the password.

## Graphics and visual design

- **Realistic, faithful illustrations.** Draw them in canvas or SVG, not clip art or stock images.
  - Equipment, cells, organisms and apparatus should look like the real thing: correct proportions, plausible materials (glass, liquid menisci, agar, plant tissue), soft lighting and shadows.
  - Labels use the site's typography.
- **Draw what the science says.**
  - Organelles, chromosomes, gels, colonies and plants must be in the right places and quantities for the current state of the simulation, and change as the data changes.
  - Every visual state must match the numbers in the tables and graphs.
- **Labels point at the exact drawn structure.** Compute leader-line anchors from the geometry you actually draw, since cell size and organelle positions change. Never hard-code coordinates. Mark the anchor point with a dot.
- **Design tokens.** Use the tokens in `style.css` (colors, radii, fonts, spacing).
  - Every graphic must work in light **and** dark mode, with text contrast at WCAG AA.
  - Never rely on color alone: add shapes, outlines, glyphs or text (✓, "CHANGED", patterns) for color-blind users.
- **Canvas.**
  - Scale for `devicePixelRatio` so drawings are crisp.
  - Set a `role` and `aria-label`.
  - Keep a text description of the current state up to date for screen readers.
- **Charts.** Use `Lab.chart` and its conventions:
  - axis titles with units
  - sensible ranges (never a pH axis of 0–15 for pH 3–10 data)
  - labels that don't break inside numbers or overlap
  - error bars where there are replicates
  - legends, and a data table alternative
- **Layout.**
  - Every visual fits its container from 375 px to 1920 px without clipping or sideways scrolling.
  - Enlarged and full-screen views scale to fit the whole window.
  - Nothing important is hidden behind sticky bars or buttons.
  - Reserve space so pages don't jump while loading.
- **Motion.**
  - Purposeful and smooth, at about 60 fps.
  - Respect `prefers-reduced-motion`; the final state must look complete without animation.
  - Never block the main thread for long. Draw offscreen work lazily, for example when it scrolls into view.
- **Delight serves learning.** Replays and timelapses, satisfying feedback on correct work, and a clear "Round complete" or "Game over" moment are welcome, but never at the cost of clarity or accuracy.

## Simulations and data

- **Base every model on the real protocol and source values:** the AP Biology Investigative Labs manual for labs 1–13, and the official OpenSciEd materials for companions.
  - Write the model's assumptions in code comments.
  - Also write them in the page's "What this simulation models" section: what is modeled, what is simplified, and how real results differ.
- **Simulated data should look like real classroom data:**
  - realistic magnitudes and units
  - biological variability between replicates
  - measurement noise and rounding like real instruments
  - plausible edge cases, such as a sensor plug reaching the end of a capillary or a gel run too long
- **It must never be impossible:** no negative masses, no frequencies above 1, no division by zero, no NaN.
- **Each student gets their own dataset.**
  - Use the seeded randomness tied to the student's Dataset ID, so results are unique, reproducible after a reload, and consistent in reports.
  - Timed experiments must keep running correctly across reloads: store timestamps, not timers.
- **Recompute everything derived from data** (key results, verdicts, prompts, report text) whenever the stored data changes. Remove stale "✓ correct" marks the moment their inputs change.
- **Make the payoff observable.** If a rare outcome matters to the lesson (a cancer-state cell, a transformed colony), give students a way to find and inspect it.
- **Validate models** with independent reference calculations in tests (see `tests/t59-science.js`):
  - Compare outputs against hand-computed values.
  - Check plausibility across several student identities.
  - Check invalid inputs.
- **Calibrate rates** so the lesson's intended pattern appears without exaggeration. For example, cancer must not look inevitable.
- **Label simulated data as simulated** everywhere it appears, including exports.

## Workflow

- **Never push to `main`.** Work on a branch, with one branch and pull request per related batch. Push once per batch, because each push restarts CI. The owner merges.
- **Check what others are doing first.** Before changing anything, fetch `origin` and read recent commits and open PRs; other agents also work on this repo. Don't overwrite their work: build on it or ask.
- **Keep changes targeted.** No broad refactors unless they fix a demonstrated problem.
- **Write clear history.** Commit messages say what changed and why. PR descriptions list the changes, the tests, and anything the owner must decide.

## Testing and verification (required for every change)

- **Running tests.** Tests are plain Playwright scripts in `tests/` (see `tests/README.md`). Run them with `NODE_PATH=$(npm root -g) node tests/<file>.js`, or `node tests/run-all.js <group>`.
- **Prove each fix.** For every bug fix, write a test that **fails** on the old code and **passes** on the fix, and report both counts. Don't weaken an assertion to make a test pass: fix the defect, or show that the test encoded wrong behavior.
- **Close everything.** Tests must close every browser and server they open, or they hang.
- **Look at your work, not just at the tests.** For any visual or simulation change:
  - Take screenshots at 390 px dark, 768, 1366 light and 1920, in several simulation states (beginning, middle, end, rare outcomes), and inspect them.
  - Check that labels point at the right parts, nothing is clipped or overlapping, the visuals match the data, and dark mode works.
  - Compare before and after when changing an existing graphic.
- **CI failures.** Treat GitHub "Input/output error" or "Bus error" failures as infrastructure and rerun them. Investigate everything else.

## Quality bar

- **Accessibility:**
  - keyboard operable, with visible focus
  - one live region for announcements
  - no color-only cues
  - reduced motion respected
  - 24 px minimum targets
  - axe clean (`tests/t59-a11y.js`)
- **Performance:** no layout shift on load (CLS ≤ 0.1) and no long blocking tasks on load (`tests/t59-perf.js`, `tests/t58-cls.js`).
- **Wording:** plain, short and friendly for high-school students, with accurate units and correct singular/plural forms.

## Science and sources

- **Accuracy comes first.** Check every model, number, drawing and explanation against the source.
- **OpenSciEd companions follow the official rules and printed card wording exactly.** This is the owner's decision. Presentation around them (labels, notices, layout) may change; the rules may not, unless the owner approves.
- **Careful cancer framing:** the game is a model, cancer is not inevitable, and nothing is a diagnosis.

## Outside audits

Verify every finding against the code before acting; many are false positives, for example from tools that strip scripts or attributes. Report which findings were real, fixed, not reproducible, or rejected, and why.

## Working with the owner

- **Ask before big decisions.** Ask before changing rules, science, branding or anything public-facing that isn't clearly specified. Otherwise pick the sensible option and say which you picked.
- **Report plainly.** Say what changed, how it was verified, what's left, and what needs the owner's decision. Keep it short.
- **Conserve usage.** Don't re-run whole suites locally when CI will; batch changes.
